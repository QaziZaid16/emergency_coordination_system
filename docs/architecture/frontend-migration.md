# Website frontend migration

## Current architecture

The maintained website is `web/react-dashboard/` (Vite, React, TypeScript). FastAPI remains the authorization and workflow boundary. The Flutter app remains unchanged; Flutter Web compiles separately to `build/web/` using the template and metadata under `web/`.

The Vercel project uses Root Directory `web/react-dashboard`, with `npm ci`, `npm run build`, and `dist` paths relative to that directory. `web/react-dashboard/vercel.json` configures those commands and the dashboard/activation rewrites. Vite copies the shared logo from `web/assets/`, so the Vercel **Include source files outside of the Root Directory** setting must be enabled. `/` and `/admin` serve the dashboard. `/activate` and `/activate.html` serve the React invitation activation screen. Existing invitations generated by FastAPI continue to use `${PUBLIC_APP_URL}/activate.html#token=...`.

## Migrated static behavior

| Prior static behavior | React implementation | Existing API contract |
|---|---|---|
| Admin login, verified session restore, logout, scoped navigation | `src/auth/session.ts`, `src/app/Dashboard.tsx` | `/auth/login`, `/auth/me`, `/auth/logout` |
| Operational overview, status pipeline, priority list, analysis/workload, attention and audit activity | `Overview` in `src/app/Dashboard.tsx` | `/admin/dashboard`, `/incidents`, `/admin/responders`, `/notifications`, `/admin/analytics`, `/admin/audit` (requested only where the account permission allows) |
| Incident search, status/priority/category filters, detail and update history | Incident queue and details in `Dashboard.tsx` | `/incidents`, `/incidents/{id}`, `/incidents/{id}/updates`, `/incidents/{id}/report` |
| Incident actions and assignment recommendations | Assignment dialog and incident controls in `Dashboard.tsx` | `/admin/incidents/{id}/recommendations`, `/assign`, `/reassign`, `/resolve`, `/cancel`, `/report/review`, `/analysis/retry` |
| Responder directory, invitation, resend, capability, availability and active state | Responders view and dialogs in `Dashboard.tsx` | `/admin/responders`, `/admin/invitations/responders`, `/admin/invitations/responders/{id}/resend`, `/admin/responders/{id}/capabilities`, `/availability`, `/admin/users/{id}/active` |
| User list, active state and incident history | User view in `Dashboard.tsx` | `/admin/users?role=user`, `/admin/users/{id}/active`, `/incidents` |
| Resource inventory and current allocations, with incident links | Resources view in `Dashboard.tsx` | `/admin/resources` (including API-returned `allocations`), `/incidents/{id}` |
| Operational summaries, daily submissions, status/category charts and filter drill-down, JSON export | `Reports` in `Dashboard.tsx` | `/admin/analytics?days=7|30|90` |
| Audit, in-app notifications/read state, scoped Co-Admins, automatic assignment policy | Corresponding views in `Dashboard.tsx` | Existing `/admin/audit`, `/notifications`, `/admin/coadmins`, `/admin/automation` contracts |
| Fragment/query invitation tokens, browser-history scrubbing and password acceptance | `src/app/Activation.tsx`, route selection in `src/main.tsx` | `/auth/accept-invitation` |

The activation screen prefers fragment tokens and supports outstanding query-token links. It scrubs the token before React renders. Hosted activation requires the configured HTTPS `VITE_ECS_API_ORIGIN`; loopback HTTP is accepted only during local loopback development. API requests reject redirects.

## Deliberately retained web files

- `web/index.html`, `web/manifest.json`, `web/favicon.png`, and `web/icons/` are Flutter Web source metadata/assets. Flutter output remains `build/web/`.
- `web/assets/brand/official-logo.svg` is copied by Vite's configured public directory and is shared by React.
- FastAPI route contracts, authorization rules, migrations, Android API configuration, and Flutter code are outside this website migration.

## Verification boundaries

React tests use mocked API responses to verify UI requests and error handling; they do not prove live credentials, hosted CORS, mail delivery, a real invitation redemption, or deployed route behavior. The production build requires the real HTTPS API origin supplied through Vercel's `VITE_ECS_API_ORIGIN`. `VITE_ECS_ALLOW_UNCONFIGURED_BUILD=true` is only for compile-only CI verification and must not be configured in Vercel. Provider account access and deployment are separate owner actions.
